Standing up an
assistant at zero cost

Build note · Microbiota assistant · Four days

Summary§1

We built an assistant for a supplement brand that answers questions about gut microbiota. It went live in four days. The hard part was not choosing a model; it was accepting that the budget limit was not a detail but the constraint that shaped the architecture. What follows is what happened, in order — corrections and one wrong turn included.

The start§2

The job began with a link to a conversation. There was no specification, just a brief along the lines of “turn the subject of this conversation into an assistant app.” That is a better starting point than it sounds: a specification tells you what the product is, while a conversation carries what people actually ask. The second is worth more, because the assistant’s job is not to describe the product but to answer the question.

The first cut drew the scope wrong§3

In the first version I wired every question to the brand’s knowledge base. Anything without an entry there got “that is not in my knowledge base.” Correct on paper, useless in practice.

It broke on a question like this: for patients with hypertension and diabetes, which probiotic strains matter most, and which prebiotics suit those strains best? The brand’s product is one example inside that question — not its boundary. Pulling the assistant’s limit down to the product reduces it to a catalogue front end.

So the scope was split in two:

The brand layer. Product positioning, red lines, what may and may not be claimed. This layer is binding: with no entry it says “not in my knowledge base” and invents nothing.

The scientific field. Strains, mechanisms, doses, clinical evidence. Here it does not go silent. Nor is it free: a strain code is written in full as genus + species + strain, every claim carries an evidence label (meta-analysis, randomised trial, observational, animal, in vitro), and drug-interaction warnings are never dropped.

An assistant saying “I don’t know” is bad; sounding certain without naming a source is worse. The format rules on the second layer exist for exactly that.

A budget limit is a design constraint§4

“How do I run this for free?” determined the rest of the project. The search had two stops.

A local model. A model installed on my own machine looks like it solves everything — until you remember the app has to run on a server, not on my desk. Local models are good for development, not for shipping.

Free cloud models. The free tier works, but you pay for it in uncertainty rather than money: requests join a queue, a model occasionally disappears, an answer sometimes takes minutes.

The lesson here is not which model won. Deciding to stay free is not a preference to optimise later; it is a constraint that shapes the architecture from the first day. Both sections below are consequences of it.

Why not Vercel§5

Free models answer in one and a half to five and a half minutes. On Vercel’s free plan, serverless functions are cut off at sixty seconds. The platform was closing the connection before the model could finish; the error that surfaced looked like a model problem, when the real limit was the ceiling itself.

We moved the app to an environment that allows long-running requests (Render). The slowness of a free model is not a defect but a known cost — the hosting side had to be able to absorb it.

Working with a second agent§6

I was not the only assistant touching the codebase: a second agent ran inside the editor, wired to a cheap, fast model. I wrote it a long rules file — what to do, what never to do, with the reasoning for each.

The agent wrote a file of unsourced clinical figures into the knowledge folder. The rules file did say “never invent a study, a number or a strain code”; the small model did not see that line among the reasoning around it.

Three things changed. The file was deleted. The project had not been under version control until that day — the git repository was created right then, because not being able to see what an agent changed was the actual problem. And the rules file was rewritten: the reasoning was cut short, the prohibitions were put in the imperative, and write access to the knowledge folder was removed entirely.

Small, fast models skip long justifications and obey short, absolute prohibitions. A rules file is not a persuasive essay; it is a list of boundaries.

A wrong turn§7

This one started with the assistant I was working with rather than with me — but I am the one who paid for it, so it belongs here.

A provider’s name came up mid-conversation. I repeated the sentence. The other side read that as “let’s do it” and switched the entire provider configuration. The next day I found myself asking why we had opened an account with that provider at all Correction — and fairly so: I had not approved it, I had only echoed what was said.

Undoing it was not hard, but it cost hours. The rule that came out of it applies to both sides: repeating a name is not approval. On decisions that change the architecture, one explicit sentence of consent is cheaper than a half-hour rollback later.

28 August: the queue§8

Today the app started timing out. The cause was not in the code: the free model tier was busy, requests were waiting in a queue, and now and then the model itself returned nothing.

The easy fix was obvious. The paid variant of the same model costs about $0.003 per question — a few dollars a month in practice. We did not take it. The account deliberately sits at zero balance; here “free” is not an aspiration but a line in the specification.

So the fix was sought in resilience rather than in budget: several free models were arranged into a fallback chain. If one queues or disappears, the request moves to the next; timeouts are defined inside the app; a half-finished answer is not thrown away.

The system is still slow — but the slowness is now expected behaviour rather than a fault. The difference shows in what you tell the user: saying “free models are busy right now, your request is queued” instead of “an error occurred” turns the same delay from a malfunction into a status report.

Three notes left over§9

One. State the constraint early. “This has to be free” is an architectural decision on day one and a rollback on day four.

Two. Do not try to persuade an agent in its rules file. Write short prohibitions in the imperative and keep the reasoning somewhere else.

Three. Repeating a sentence is not approval. Whether the other party is a person or a model, ask for explicit consent on decisions that are expensive to reverse.
